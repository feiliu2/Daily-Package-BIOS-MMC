DAILY BUILD / WINDOWS + LINUX

每日 BIOS 打包
与匹配 MMC 固件

从 Artifactory 获取最新 BIOS，按 IFWI 仓库中的 biosid_oak_ap.xlsx 映射，用本仓库的 Python 代码直接重组 BIOS ID 包。随后从 BIOS 中读取 MMC 版本，生成对应的固件包。加上 --upload 后，用环境变量中的 Token 上传并校验两个包。

Windows / Linux 同一套代码 不依赖 OakStreamAPIfwi 源码 MMC 跟随 BIOS 版本 上传需显式 --upload

FINAL DELIVERABLES

C:\LocalPath\Bios\    (Linux: ~/LocalPath/Bios/)
├── 0040.D79.7z
└── MMCFW_0.1022.0.7z

BIOS + 匹配的 MMC；输出目录中的其他文件不受影响

实际的 BIOS ID 和 MMC 版本由每次运行自动确定。

说明：本页是离线流程说明，不会执行任何命令。定时调度不在本工具范围内（Windows 计划任务或 Linux cron / systemd timer 均可调用同一命令）。

三个来源，一条版本链

最新 BIOS → 组件映射 → BIOS 内的 MMC 版本 → 精确匹配的 MMC 构建

BIOS · 查询最新 Build ID

https://af01p-or.devtools.intel.com/artifactory/server-bios-staging-local/Daily/OakStreamRp/main/

识别 OAKSTRM.0.RPB.<release>.D.<revision>/，按 release 和 revision 的数值大小选择最新版本；也可用 --bios 0040D79 指定版本。默认分支 main，可用 --bios-branch 换成 dmr_ap1_b0_po_platform、oks_milestone_rel 等其他分支目录。

映射 · biosid_oak_ap.xlsx

每次运行都从 GitHub 仓库 intel-innersource/firmware.boot.uefi.iafw.devops.build.ifwi 的 oak_release/BuildScripts/CommonLib/BIOS_Repackaging/ 拉取，默认 release/ap.post-silicon 分支（该仓库的 main 分支里没有这个文件），需要设置 IFWI_GITHUB_TOKEN（FIV Ubuntu 镜像 v1.1.3 起已内置）。拉取失败直接报错，不回退到旧缓存。

MMC · 查询 BIOS 指定版本

https://af01p-or.devtools.intel.com/artifactory/server-bios-staging-local/Daily/ZCodeFW/zcode_dmr_ap_dev/

默认分支 zcode_dmr_ap_dev，可用 --mmc-branch 切换。在分支中找到唯一的 MMC_FW.[前缀.]<version>/ 目录（不同分支命名不同，如 MMC_FW.DMR_AP.0.999.0/、MMC_FW.0.915.2/），再进入 DMR_ZCODE_DebugSigned_linux/。不会选择另一个更高但与 BIOS 不匹配的 MMC 版本。

端到端执行流程

先完成 BIOS 阶段，再进入 MMC 阶段

正常入口：手动或由调度器执行完整流程。单独执行某一步：main.py bios 只打包 BIOSID，main.py mmc --bios-archive 只补打 MMC，main.py upload 只上传。补打 MMC 时直接从第 05 步开始，不读取映射，也不重新打包 BIOS。

A

BIOS 打包

原 restructure_new.py 的逻辑，用本仓库代码重新实现

  1. 01

    读取组件映射

    解析 xlsx 的 config sheet：Original Package / Original Binary / Original Folder / Package file，按包和文件夹分组。只用 Python 标准库解析，不需要 pandas 或 openpyxl。日志记录映射来源和 SHA-256。

    当前映射：10 个组件包，553 行
  2. 02

    发现 BIOS 与组件包

    在构建目录中找到每个 Original Folder（优先精确同名），再按索引时间取匹配 Original Package 的最新文件。

    OAKSTRM.0.RPB.0040.D.79/
        ↓
BIOS ID: 0040D79
Archive: 0040.D79.7z
  3. 03

    并行下载解压，按序复制

    • 下载和 7-Zip 解压并行进行（--jobs）。包被截断或损坏时自动重试（--download-retry，默认 3 次）。包内有 IFWIStitch20.bin 时再解开一层。
    • 复制按表格顺序逐个组件进行。路径统一转成 \ 分隔后匹配，所以原有正则在 Linux 上结果相同。
    • Fv*Path.dsc 按原脚本方式拼接，与原 Windows 输出逐字节一致；BinaryFvSpr.fdf 中的 S3M 路径会被改写。
  4. 04

    汇总、压缩、校验、发布

    显示组件包总数、已打包和未打包数量，并列出未打包的组件及原因。和原脚本一样，缺少文件的组件不会阻止整体打包。

    暂存目录建在输出目录下的 bios-* 中。压缩后先执行完整的 7z t，再原子替换同名包，最后删除暂存目录。不再使用 C:\ATF，也不再清空输出目录。

    所有组件都失败 → 不发布，保留旧包
B

匹配 MMC 打包

从已生成或显式指定的 BIOS 压缩包开始

  1. 05

    从 BIOS 读取 MMC 版本

    读取所有 Trunk_*/dsc/FvRawDefPath.dsc，检查 DEFINE MMC1 和 DEFINE MMC2 指向的 mmc_pkg_<version>_...。

    必须得到唯一且一致的版本，缺失或冲突时直接失败。

  2. 06

    定位精确匹配的构建

    MMC_FW.DMR_AP.0.1022.0/
└── DMR_ZCODE_DebugSigned_linux/
    └── *_BuildPkg.7z

    版本目录在分支中必须恰好匹配一个（MMC_FW.DMR_AP.0.1022.0/ 或 MMC_FW.0.1022.0/），其中必须恰好有一个 _BuildPkg.7z，不回退到其他版本。

  3. 07

    下载并只提取 binaries

    • 只提取 binaries 子树，包括其中的许可证文件。
    • 不混入索引目录里的散装 .bin。
    • 拒绝不安全路径，以及 binaries 内的链接。
  4. 08

    重打包、逐项验证、发布

    MMCFW_0.1022.0/
└── binaries/
    ├── LICENSE-*.txt
    └── mmc_pkg_0.1022.0_...bin

    完整执行 7z t，确认路径、大小和 CRC 都与源 binaries 一致后，原子替换同名包，然后清理 mmc-fw-* 暂存目录。BIOS 包不会被改动。

运行命令

Linux 用 python3 和 export；Windows 用 python 和 $env:

前置条件

  • Python 3.10 或更新版本（只用标准库）。
  • 原生 7-Zip：Windows 安装 7-Zip 即可；Linux 安装 7zip 或 p7zip-full；也可以用 --seven-zip 指定路径。
  • IFWI_GITHUB_TOKEN：需要能读取 IFWI 仓库，用于拉取映射表。使用 --mapping-xlsx 指定本地文件时可以不设置。
  • 能访问 Intel 网络或 VPN；代理遵循 HTTP(S)_PROXY / NO_PROXY 环境变量。

上传（Token 来自环境变量）

默认不上传；完整流程加 --upload，或单独使用 upload 子命令

只上传现有压缩包

预览：不读 Token，不发出 HTTP 请求 
python3 main.py upload --dry-run
实际上传 
export IFWI_ARTIFACTORY_TOKEN=...
python3 main.py upload
python3 main.py upload --bios-archive ./0040.D82.7z --mmc-archive ./MMCFW_0.1022.0.7z

不指定文件时，--source-dir 中必须恰好有一个 BIOS 包和一个 MMCFW_版本.7z，不会自动选择最新的文件。

预检、直传、校验

BIOS → DEG-IFWI-LOCAL / FIV_Portal / IFWI_CI / BIOSID

MMC → DEG-IFWI-LOCAL / FIV_Portal / IFWI_CI / MMC

以上为默认目标，可用 --upload-url（https://<host>/artifactory/<仓库>）、--upload-bios-path、--upload-mmc-path 修改；完整流程、mmc --upload 和 upload 都支持。

  • 上传和下载共用同一个 IFWI_ARTIFACTORY_TOKEN（FIV Ubuntu 镜像中已内置）。上传时缺失或格式不对，在发出任何请求前就失败；下载时如果没有设置，就匿名访问。
  • 先预检两个目标目录和同名文件：内容相同则跳过，同名但内容不同则停止，不会覆盖。
  • 上传使用 HTTP PUT，附带 X-Checksum-Sha256；传输过程中本地文件如有变化，也判定为失败。
  • 上传后核对远端路径、字节数和 SHA-256，一致才算成功。

Token 不会出现在命令行和日志中。

清理边界与失败分支

出错时写日志并返回非零退出码，不静默回退，也不把失败当成功

输出目录：只替换目标包

只替换本次生成的同名包，不删除输出目录中的其他文件。拒绝使用根目录、家目录、本仓库目录、链接或 junction 作为输出目录。

BIOS：部分缺失只警告

组件文件夹不存在、下载失败或文件缺失时，该组件记为未打包，其余组件照常打包，与原脚本行为一致。所有组件都失败时不发布，保留旧包。

MMC 失败：不破坏 BIOS

版本缺失或冲突、源包缺失或不唯一、网络、解压或校验失败时都会报错。只清理本次的暂存目录；新包校验通过之前，不替换已有的同名 MMC 包。

暂存清理：只重试可恢复的锁定

遇到 Windows 文件锁定（错误 32、33）时，最多重试 5 次，每次间隔 2 秒。其他权限问题直接报错。

加 --upload 时先查目标仓库

同样的内容重新打包，SHA-256 也会变（7z 记录了文件修改时间）。如果不预先检查，已经发布过的版本会被白白重打一遍，而且上传时会因同名但内容不同而失败。所以加了 --upload 后，打包前会先查目标仓库：BIOS 已存在就不重新打包，改用与远端一致的本地副本，本地没有或不一致就下载远端那份并校验；MMC 已存在就不打包也不上传；两者都已存在则直接以 0 退出。token 缺失会在打包前就报错。不加 --upload 时不访问目标仓库。

上传失败：保留产物，单独重试

上传或校验失败时返回非零，保留本地文件。如果 BIOS 已成功而 MMC 失败，不删除远端已校验的 BIOS。用 upload 子命令重试时，相同的文件会自动跳过。

排查日志：控制台输出与脚本旁的 logs/package-bios-YYYYMMDD.log 内容相同。日志记录映射来源和 SHA-256、每个组件的 URL、打包和未打包的汇总、MMC 的选择，以及上传结果。
